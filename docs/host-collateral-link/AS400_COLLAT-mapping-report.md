## 6. ประเด็นที่ต้องตัดสินใจ

### 6.1 ⭐ หลักประกันชิ้นเดียวได้เลข AS400 หลายตัว — เราเก็บได้ตัวเดียว

**เป็นเรื่องใหญ่ที่สุดในรายงานนี้** และเกิดสองชั้น

**ชั้นที่ 1 — หลายเลขต่อหนึ่งใบประเมิน** · 952 เลขที่ประเมินถือเลขหลักประกันรวม **9,335 ตัว** เก็บได้ 952
→ ทิ้ง 8,383

| | |
|---|---|
| block project (ที่เราคาดไว้) | 78 |
| **หลักประกันธรรมดา ไม่ใช่ block** | **732** |
| ไม่มีใบประเมินในระบบ | 142 |

ใบเดียวมีได้ถึง **455 เลข** · เราเคยเข้าใจว่าเป็นเรื่องของ block project เป็นหลัก **ข้อมูลจริงบอกตรงข้าม**

**ชั้นที่ 2 — หลายใบประเมินชี้มาที่หลักประกันเดียวกัน** · 801 master ถูกอ้างโดยมากกว่าหนึ่งใบ
→ ทิ้งอีก 1,142

**และทั้ง 801 master นั้น เลข AS400 ที่แต่ละใบพามาไม่ตรงกันเลยสักคู่**

แปลว่าไม่ใช่ข้อมูลซ้ำที่ไม่มีผล มีสองความเป็นไปได้ ซึ่งต้องให้ธุรกิจกับ AS400 ช่วยชี้

- dedup ของเรา**ยุบมากเกินไป** — รวมสิ่งที่ AS400 ถือว่าเป็นคนละหลักประกัน
- หรือ AS400 **ออกเลขใหม่ทุกครั้งที่มีวงเงินใหม่** บนหลักประกันเดิม ซึ่งโมเดลช่องเดียวของเราแทนไม่ได้

> เชื่อมโดยตรงกับงาน **แยก master รายประเภท** ที่พักไว้ — แต่ลำพังการแยกรายประเภทยัง**ไม่พอ**
> แก้ได้แค่ส่วนหนึ่ง เพราะปัญหานี้เกิดกับหลักประกันประเภทเดียวกันด้วย

### 6.2 ตัวนับของ job ไม่ balance

```
received=27727  updated=21791  unchanged=0  notFound=4691  projectSkipped=103
27727 − 21791 − 4691 − 103 = 1142 หายไปโดยไม่มีหมวด
```

1,142 คือชั้นที่สองในข้อ 6.1 ซึ่ง**ไม่มีตัวนับรองรับ** คนที่ดู log จะบวกไม่ลงตัวและไม่รู้ว่าหายไปไหน
**เป็นข้อบกพร่องของโค้ดที่ผมเขียนเอง** ควรเพิ่มตัวนับ `CollapsedToSameMaster` ให้ครบ

### 6.3 ชื่อไฟล์ที่ AS400 ส่งมา job รับไม่ได้

ไฟล์จริงชื่อ **`AS400_COLLAT.txt`** แต่ระบบต้องการ `AS400_COLLATLINK_<YYYYMMDD>.txt`
· ไม่ match glob → ไม่ถูกหยิบ · ต่อให้แก้ glob `ParseFilenameDate` ยังคืน `null` แล้ว **quarantine ทั้งไฟล์**

รายงานนี้ทำได้เพราะผม**เปลี่ยนชื่อไฟล์เอง**เป็น `AS400_COLLATLINK_20260630.txt` (วันที่จาก header)
· ต้องตกลงกับ AS400 ว่าจะใช้ชื่อไหน หรือแก้โค้ดให้ยอมรับชื่อที่ไม่มีวันที่ (แล้วใช้วันที่จาก header แทน)

## 8. เลขที่ขึ้นต้นด้วย `B` = block project (ตรวจเพิ่มตามที่ธุรกิจแจ้ง)

### 8.1 ✅ ตัด `B` แล้วแมพได้ 100%

`B` + เลขมาตรฐาน 8 หลัก (เช่น `B62A00645` → `62A00645`) · **107 เลขแมพได้ครบทุกตัว 705 แถว**

**ปลอดภัย** — เลขที่ประเมินของเราไม่มีตัวไหนขึ้นต้นด้วย `B` เลย (0 จาก 59,292) จึงไม่มีทางไปทับของจริง

จาก 107 เลข — **97 เป็น block project จริง** · 10 ตัวไม่ใช่ (1 เป็น LB ธรรมดา · 5 เป็น `Progressive`
ที่มีแต่ property อาคาร · 3 เป็นคอนโด) จึงใช้ `B` เป็นตัวชี้ block ได้ **แต่ไม่ 100%**

### 8.2 🔴 แต่ตัด `B` แล้วนำเข้าตรง ๆ **อันตราย**

ตัวอย่างจริง `63A01755`

```
63A01755   id=87141  D          ← ไม่มี B: เลขเดียว (ตัวโครงการ)
B63A01755  id=86385  D          ← มี B: ห้าเลข (รายยูนิต)
B63A01755  id=88733  D
B63A01755  id=89515  D
B63A01755  id=90364  R   ←← มียูนิตที่ไถ่ถอนแล้วปนอยู่
B63A01755  id=91017  D
```

**47 จาก 107 เลข ปรากฏทั้งแบบมี `B` และไม่มี `B`** และวันที่ในไฟล์เป็น `01072026` เหมือนกันหมด

ถ้ายุบรวมกันแล้วให้ `PickWinningRecord` เลือกตัวเดียว — กติกา "วันเท่ากัน `R` ชนะ `D`" จะทำให้
**42 โครงการที่ไถ่ถอนแค่บางยูนิต ถูกทำเครื่องหมายว่าไถ่ถอนทั้งโครงการ** แล้วหลุดจากรายงานผู้กำกับทั้งก้อน

> นี่คือความเสียหายแบบเดียวกับที่ guard `projectSkipped` ถูกสร้างมาเพื่อป้องกัน — การตัด `B`
> แบบไม่ระวังจะพามันกลับมา

**ผลถ้าตัด `B` (จำแนกใหม่ทั้งไฟล์)** — 705 แถวย้ายออกจากกลุ่ม "ไม่รู้จัก" แต่ **master ที่ได้เลขเพิ่มขึ้นแค่ 1**

| แมพได้ | 22,933 | 22,934 |

**คุณค่าที่แท้จริงคือด้านการวินิจฉัย** ไม่ใช่การเขียนข้อมูลเพิ่ม — 705 แถวเปลี่ยนจาก "ไม่รู้ว่าคืออะไร"
เป็น "รู้ว่าเป็นยูนิตของโครงการไหน"

### 8.3 ⚠️ `B` คือเครื่องหมาย block แต่**ยังไม่บอกว่ายูนิตไหน**

เราคาดว่า CCSURV จะเป็น **เลขที่ประเมิน 8 หลัก + ลำดับยูนิต 2 หลัก** ตามที่ AS400 ยืนยันเมื่อ 13 ส.ค.
**ไฟล์จริงไม่มีรูปแบบนั้นเลย** — เลขที่ยาว 10 ตัวมี 119 เลข แต่เป็นรูปแบบ `2559100086`
(ปี พ.ศ. + running) และ **ไม่ match ทั้งแบบเต็มและแบบตัด 8 ตัวแรก**

แปลว่าปัญหาเดิมยังอยู่: รู้ว่าเลขนี้เป็นของโครงการไหน แต่**ไม่รู้ว่าเป็นยูนิตไหน** จึงยังเขียนลง
`ProjectUnits.HostCollateralId` ไม่ได้ · **ต้องกลับไปคุยกับ AS400 ว่าตกลงส่งลำดับยูนิตมาทางไหน**

## 9. ตรวจสอบข้ามด้วยเส้นทางที่สอง — ยืนยันว่าการแมพถูกต้อง

U3 มีเลขหลักประกันเดิมจากระบบเก่าติดมาด้วย (`LandTitles` 21,131 · `BuildingAppraisalDetails` 18,224
· `CondoAppraisalDetails` 6,155 · `MachineryAppraisalDetails` 26 · `appraisal.ProjectUnits` 166)
จึงแมพด้วย **เลขหลักประกัน** แทนเลขที่ประเมินได้อีกทาง

### 9.1 ✅ สองเส้นทางตรงกัน 99.8%

| | |
|---|---|
| เลขที่แมพได้ทั้งสองทาง | 22,197 |
| **ตรงกัน** | **22,156 (99.8%)** |
| ไม่ตรงกัน | 41 |

เป็นการยืนยันแบบอิสระว่าการแมพด้วยเลขที่ประเมินถูกต้อง · 41 ตัวที่ไม่ตรงควรตามดูเป็นรายกรณี

### 9.2 ❌ แต่กู้แถวที่แมพไม่ได้แทบไม่ได้เลย

| กลุ่ม | แถว | มีเลขในข้อมูลเดิม |
|---|---|---|

ไม่ใช่แค่แมพพลาด

## 10. กลุ่ม `99` — ก้อนที่ไม่รู้จักใหญ่ที่สุด

| | |
|---|---|
| แถว / เลข | 2,129 / 2,128 (เกือบทั้งหมด 1 เลขต่อ 1 หลักประกัน) |
| รูปแบบ | `99A00001` เรียงต่อเนื่องจาก 1 |
| D / R | 1,203 / 926 — **ไถ่ถอนแล้ว 43%** สูงกว่าค่าเฉลี่ยทั้งไฟล์ (21%) เท่าตัว |
| ช่วงเลขหลักประกัน | 122 – 110,099 |

ช่วงเลขทับซ้อนกับกลุ่มที่แมพได้ (60 – 141,803) แสดงว่า**ไม่ใช่ของเก่าที่ตกยุค** แต่ออกเลขสลับกันมาตลอด
· `99` ไม่ใช่ปี พ.ศ. และรหัสประเภทท้ายแถวก็เป็นประเภทปกติ

**สมมติฐานที่ต้องให้ AS400 ยืนยัน** — น่าจะเป็นหลักประกันที่ขึ้นทะเบียนใน AS400 โดยตรงไม่ผ่านการประเมิน
ในระบบเรา (เช่น เงินฝากค้ำประกัน หลักประกันที่รับโอนมา) ถ้าใช่ ก็**ไม่ควรคาดหวังให้แมพได้**
และควรแยกออกจากตัวเลข "แมพไม่ได้" เพื่อไม่ให้ดูเหมือนระบบมีปัญหา
