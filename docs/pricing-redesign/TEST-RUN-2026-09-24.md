## New finding — `Weight` is stored to 5 decimal places

`appraisal.PricingCalculations.Weight` is `decimal(10,5)`. Three equal comparables are saved as
`0.33333` each, which sums to 99.999%, not 100%.

While the old code summed unrounded products the arithmetic hid it (the total came out as if the
weight were exactly ⅓). Now that each step is rounded and stored, recalculating from the saved data
cannot reproduce ⅓, so the method's rate came out 0.72 lower — on this method ~2,880 baht over
4,000 sq.wa.

This is a pre-existing data-model limit, not something the rounding change introduced; the change
only made it visible by making the stored parts agree with the stored total. It reaches money
wherever a Role=Land method feeds LandValue. Worth a decision:

- widen the column (e.g. `decimal(10,8)`), or
- normalise weights server-side so they total 1, or
- leave it and accept 0.001% on equal-weight sets.

I have not changed anything here.

# Code review — 15 rounds

Run to the cap you set. The loop was worth it: rounds 1-2 found defects in the original work, and
rounds 3-14 mostly found defects in *my own fixes* — five rounds running. The pattern was always the
same shape: patching one condition at a time on code whose ordering matters, without tracing the
whole path first. The one place I stopped patching and rewrote from the definition
(`ThaiLandAreaFormatter`) passed on the next round and every round after.

## Fixed (17)

**Ordering and guards**
- `SyncLandValueWithIndicatedValue` ran before the role was settled, so ticking "include building"
  copied the combined land+building total into `LandValue` and unticking skipped the sync entirely.
- The same call then ran before `SetValue` stamped the unit on the manual-cost path, so it silently
  did nothing on a method's first save and fixed itself only if you saved twice.
- The `!isCostApproach` clear sat ahead of the "no titled land" guard and wiped the land-area
  override that `CreateReferenceFromMethod` puts on DCF land references.

**The land gate**
- Keyed on `Role` being null, which is also true of cost rows that predate Role — those would have
  lost real land values on the next save of any kind. Now keyed on the approach type.
- `IncludeLandArea` became a one-way switch for non-cost methods: unticking and re-ticking left it
  false, permanently dropping the พื้นที่ / ราคาต่อหน่วย columns from that group's book row.

**The indicated-value stamp** (`UpdateMethod`)
- Stamped on a remark-only save, freezing the price. Then on a calc-mode flip, because the prior
  value had been nulled. Then on a system-calculated method, because the request's flag is not the
  method's. Then never at all on a method's first price, because I had over-corrected with a
  null check. The rule that finally held: manual mode, and the value actually moved.
- `SetCalcMode` did not clear `IndicatedValue`, so a manual figure outlived the mode it belonged to;
  then it cleared on both directions, dropping the figure the appraiser was committing.

**Rounding**
- `ThaiLandAreaFormatter` rewritten to decompose the total instead of carrying component by
  component — fixes fractional rai and ngan, and the triple now reconciles with the total by
  construction.
- Manual-cost seeded `IndicatedValue` rounded twice (whole baht, then thousand), landing 1,000 baht
  from what the card shows.
- `isFullyBuilt` read the rounded progress, so 99.9951% printed an unfinished building at its
  completed price.

**Reporting**
- The construction book's ณ ปัจจุบัน row could exceed its own 100% row.
- Comments in `ConstructionCurrentValueService` and `vw_MisCasReport` asserted as present-tense fact
  something only true of rows saved since the change.
- `.gitignore` was missing `uploads/temp/`.

## One behaviour change worth knowing before deploy

`RoundFinalValue` going from floor to nearest thousand means every existing PerUnit market method can
move up by as much as 999 baht on its next recalculation — and `SaveComparativeAnalysis` recalculates
on every save, including one that only edits a remark. A job already sent to LOS at 4,999,000 can
become 5,000,000 and republish `AppraisalValueChangedIntegrationEvent`, which re-routes the approval
tier. Not a defect: it is what "match the screen" means. But it is a one-off money movement across
the estate.
