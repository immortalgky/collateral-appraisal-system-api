1. Scope and ownership

The application performs no database maintenance itself. Its background jobs (Hangfire) purge only application data: logs, outbox messages and expired report files. Index maintenance, statistics updates and integrity checks are SQL Server Agent jobs owned by the DBA, as described in this guide.

Do not grant these rights to the application login. DBCC CHECKDB needs db_owner or sysadmin, and ALTER INDEX needs ALTER on every table. The jobs below run under the SQL Server Agent service account. The application account keeps its existing least-privilege grants.
Already in place? If the bank already runs maintenance on this instance, run the optional pre-check in section 2 and skip what it already covers (verification: section 7).

2. Install: one script, run once

Everything is in one script, Database\Scripts\Maintenance\CreateMaintenanceAgentJobs.sql. It installs Ola Hallengren's SQL Server Maintenance Solution (free, MIT licence, ola.hallengren.com; version 2026-09-12 embedded unchanged, into master, with no Ola jobs and no backups) and then creates the four Agent jobs of section 3. The DBA runs it once, by hand, in SSMS, as sysadmin. It is not run by DbUp, the migrate tool or the deploy scripts, and it only needs to be run again to change a setting.

Server preparation — check before running

  • SQL Server Agent service is running and its startup type is Automatic.
  • The database server clock and time zone are Thai: SELECT SYSDATETIMEOFFSET(); must end in +07:00. Agent schedules use the server's local time; on a UTC server 22:00 would fire at 05:00 Thai time, inside the application's 01:00–05:00 window.
  • The application database exists. Optional: a dedicated database for Ola instead of master (see the script header: change @OlaDatabase and the USE [master] line in Ola's section).

Optional pre-check

On a server that might already have Ola or other maintenance jobs, run Database\Scripts\Maintenance\CheckMaintenanceSolution.sql first. It is read-only. It shows where Ola lives and its version, and any Agent job that already calls IndexOptimize or DatabaseIntegrityCheck. If such a job covers this database (USER_DATABASES, ALL_DATABASES or its name), it would maintain the database twice. Either exclude it there (@Databases = 'USER_DATABASES, -CollateralAppraisal') or do not run our script.

If Ola is already in master: the script leaves it alone when it is the same version, so running it again is safe. If it is any other version, the script stops with an error before changing anything. It never upgrades or downgrades an install that other jobs may depend on.

Then set the three variables at the top of the first batch (@DatabaseName, @OlaDatabase, @JobOwner), run the whole file in one go, and verify with section 7.

3. Job definitions

The script creates these four jobs. It checks its variables first and stops, creating nothing, if the database, owner login or @OlaDatabase is wrong. The jobs are created in one transaction. Running the script again drops and recreates only these four jobs (matched by exact name). Each job name ends with - <database>. The blocks below show what the job steps run.

3.1 Statistics — nightly

This job is cheap, and it matters most for this database (see section 5). It updates only statistics whose rows changed since the last update.

EXECUTE dbo.IndexOptimize
    @Databases              = 'CollateralAppraisal',
    @FragmentationLow       = NULL,
    @FragmentationMedium    = NULL,
    @FragmentationHigh      = NULL,     -- statistics only, no index work
    @UpdateStatistics       = 'ALL',
    @OnlyModifiedStatistics = 'Y',
    @LogToTable             = 'Y';

3.2 Index optimize — weekly

This job reorganizes indexes fragmented 5–30% and rebuilds those above 30%. It skips indexes smaller than 1,000 pages, and stops starting new work after two hours.

EXECUTE dbo.IndexOptimize
    @Databases              = 'CollateralAppraisal',
    @FragmentationLow       = NULL,
    @FragmentationMedium    = 'INDEX_REORGANIZE,INDEX_REBUILD_ONLINE,INDEX_REBUILD_OFFLINE',
    @FragmentationHigh      = 'INDEX_REBUILD_ONLINE,INDEX_REBUILD_OFFLINE',
    @FragmentationLevel1    = 5,
    @FragmentationLevel2    = 30,
    @MinNumberOfPages       = 1000,
    @UpdateStatistics       = 'ALL',
    @OnlyModifiedStatistics = 'Y',
    @TimeLimit              = 7200,     -- seconds
    @LogToTable             = 'Y';

3.3 Integrity check — weekly

EXECUTE dbo.DatabaseIntegrityCheck
    @Databases     = 'CollateralAppraisal',
    @CheckCommands = 'CHECKDB',
    @LogToTable    = 'Y';

3.4 Housekeeping — weekly

This job deletes dbo.CommandLog rows older than 30 days and purges the job history of these four jobs older than 30 days. History of other jobs is not touched.

Backups follow the bank's existing backup policy. This setup creates no backup job and never calls Ola's DatabaseBackup.

4. Schedule

The application runs its own jobs in the early morning. Heavy maintenance in the same window competes for locks and I/O, so the DBA jobs run in the evening instead.

The application times are defaults, not fixed. An administrator can move them in the application under Scheduled Jobs (/admin/job-schedules). Check the current schedules there before you fix the maintenance window. If the bank has users working at 22:00, move the DBA jobs later and keep them clear of the application window.

5. Notes specific to this database

  • Primary keys are time-ordered GUIDs (GUID v7). New rows append at the end of each index, so fragmentation grows slowly and the weekly index job is mostly a safety net. Stale statistics hurt query plans much more, which is why they are refreshed every night.
  • dbo.Logs has high churn: about 150,000 rows are inserted per day and purged again by a nightly job. It will usually be the most fragmented table, which is expected.
  • The hangfire schema (background job storage) also changes constantly. It is in the same database and is covered automatically.
  • Spatial indexes exist on geo-point columns in the appraisal, collateral and request schemas. They are slow to rebuild, and @TimeLimit keeps the job inside its window.
  • Edition: INDEX_REBUILD_ONLINE works only on Enterprise edition. On Standard edition the procedure falls back to an offline rebuild, which locks the table while it runs. That is acceptable inside the evening window.

6. Failures and corruption response

No e-mail is configured. A failed job shows in SQL Server Agent (job history, red icon) and in the queries of section 7. Check them after the first weekend and then regularly. An integrity check that fails silently is worse than none.

If CHECKDB reports corruption, do not run REPAIR_ALLOW_DATA_LOSS. Restore from the last good backup, then contact the application vendor. Repair can silently discard rows that the application needs.

7. Verification checklist

Run on: SQL ServerSSMS
-- Start the cheap job once, then read the outcome (run_status 1 = succeeded, 0 = failed; step_id 0 = whole job)
EXEC msdb.dbo.sp_start_job @job_name = N'CAS - Statistics (nightly) - CollateralAppraisal';

SELECT TOP (20) j.name, h.step_id, h.run_status, h.run_date, h.run_time, LEFT(h.message, 200) AS message
FROM   msdb.dbo.sysjobhistory h JOIN msdb.dbo.sysjobs j ON j.job_id = h.job_id
WHERE  j.name LIKE N'CAS - %'
ORDER BY h.instance_id DESC;

-- Last clean CHECKDB: should be less than 8 days old once the first Saturday has passed
SELECT DATABASEPROPERTYEX('CollateralAppraisal', 'LastGoodCheckDbTime');

-- What the jobs actually did recently (non-zero ErrorNumber = investigate)
SELECT TOP (50) StartTime, EndTime, CommandType, ObjectName, IndexName, ErrorNumber
FROM   master.dbo.CommandLog   -- or the database you used as @OlaDatabase
ORDER BY ID DESC;
  • All four jobs exist in SQL Server Agent, are enabled, and have schedules attached.
  • The Statistics job, started by hand with sp_start_job, ended with run_status = 1.
  • After the first weekend, LastGoodCheckDbTime shows that weekend's date.
  • dbo.CommandLog shows entries for CollateralAppraisal with ErrorNumber = 0.
  • No DBA job overlaps the application window shown under Scheduled Jobs (/admin/job-schedules) in the application.
