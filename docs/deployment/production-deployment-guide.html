Step 2Deploy the database (DBA — ONCE per release, BEFORE any application node is deployed)

What the db\ folder contains

#FileWhat it doesApprox. size
100_Prepare.sqlCreates dbo.DatabaseMigrationHistory, the journal table that records which scripts have run.1 KB
201_EF_01_CommonDbContext.sql
… through …
01_EF_11_ReportingDbContext.sql		 Tables, keys, indexes for all 11 modules. Each file is an EF Core idempotent script: every migration is wrapped in IF NOT EXISTS (SELECT … FROM __EFMigrationsHistory), so already-applied migrations are skipped. The numbering is the required run order — module dependencies rely on it. 7 KB – 690 KB
(~1.1 MB total)
302_Repeatable_ViewsAndProcs.sql All 61 views and stored procedures, emitted in dependency order. Each is CREATE OR ALTER, so re-running always leaves the current definition in place. ~250 KB
403_OneTime_DataScripts.sql 39 one-time reference-data and data-fix scripts (Thai province/district/sub-district tables, parameters, document types, pricing templates, meeting configuration, …). Each block is skipped if the journal already records it. ~1.9 MB
599_Verify.sqlRead-only. Run after the others and read the output.2 KB
How re-running is made safe. Three independent mechanisms, all standard:
  • EF migrations — recorded in __EFMigrationsHistory inside each module's schema (request, workflow, appraisal, …). The generated script tests that table before every migration.
  • Views and stored procedures — CREATE OR ALTER: no drop, no data loss, correct result whether the object exists or not.
  • One-time data scripts — each block starts with a lookup in dbo.DatabaseMigrationHistory. If the script is already recorded, the block turns on SET NOEXEC ON so SQL Server parses but does not execute the statements, then turns it off again and moves on. The journal row is written at the end of the block.
Consequence: if a run fails halfway, fix the cause and run the same file again. Everything already applied is skipped.

Rules

Four rules that must not be broken.
  • Run once per release, from one place. Never run the scripts concurrently from two sessions.
  • Run before deploying the application. A node that starts against an un-migrated database will either try to migrate it itself (if it has DDL rights) or fail to start.
  • Keep the numeric order. 01_EF_01 creates tables that 01_EF_03 references; 02 creates views over those tables; 03 populates them.
  • There is no automatic schema rollback. Schema changes within a release are backward-compatible so the previous application build keeps running during the rollout, but reversing a migration means restoring the pre-release backup.

Step 3Deploy the application per node (first installation — manual file copy)

The application is a folder of files: deploying it means copying two folders into place. There is no installer and no deployment program. On a first installation the target folders are empty, so this is a straight copy — nothing to back up, nothing to remove.

Do §6 first. The application pool, the two websites and the certificates must exist before the files are of any use. If §6 has not been done on this node yet, do it now and come back.

3.1 Backend — <APP_ROOT>\api

  1. Confirm the pool is stopped.
    IIS Manager▸Application Pools▸CAS▸Stop
    Not strictly required with no application running yet, but it keeps the node from serving a half-copied folder.
  2. Copy the build in. Copy the entire contents of <STAGING_ROOT>\api\ into <APP_ROOT>\api.
  3. Put the configuration file in place. Copy the appsettings.Production.json you prepared in Step 1 into <APP_ROOT>\api. The release bundle deliberately does not contain it.
  4. Confirm the folder contents. Api.dll, web.config and appsettings.Production.json are all present.
  5. Create the logs folder if it is not there, and confirm the app-pool service account has Modify on it — otherwise the application starts but writes no log, which makes every later problem harder to diagnose.
The upload limit is applied to this web.config. The file that just arrived with the build is the one §6.5 edits. Apply §6.5 after this copy, not before — otherwise the copy overwrites the change.

3.2 Frontend — <APP_ROOT>\web

  1. Copy the entire contents of <STAGING_ROOT>\web\ into <APP_ROOT>\web, including web.config — unlike the API, the SPA's web.config comes from the release, because it carries the routing rules that make deep links work.
  2. Confirm index.html, web.config and assets\ are all present.

3.3 Start the node and confirm it is healthy

  1. Start the application pool.
    IIS Manager▸Application Pools▸CAS▸Start
    Both websites share this pool, so one start covers the API and the SPA.
  2. The application starts on the first request. That first request takes noticeably longer than later ones: on a brand-new database it also seeds menus, permissions, roles, the OAuth2 client applications and the workflow, SLA and committee configuration. Give it a minute before deciding something is wrong.

Then check the two addresses on the server itself:

AddressExpected
https://localhost:7111/health/readyLoads and reports Healthy. This is what the F5 uses to decide whether the node takes traffic.
https://localhost:3000/The application's sign-in page loads.
Run on: the node just deployedCommand line alternative
# -k skips certificate validation: the cert is issued for the public host name, not localhost.
curl.exe -k -s -o NUL -w "%{http_code}\n" https://localhost:7111/health/ready
# Expect 200. If it is not 200, see §7 for how to find out which dependency failed.
If the health check does not come back within a minute or two, do not move on to the second node. Read <APP_ROOT>\api\logs\log-*.txt and the Windows Event Log (§8.1) — the first start is where a wrong connection string, a missing certificate permission or an unreachable dependency shows up.

3.4 Then the second node

Repeat 3.1 to 3.3 on node 2, using the same release folder and the same appsettings.Production.json values — the certificate thumbprints, database connection string and AppBaseUrl must be identical on both nodes, or tokens issued by one node are rejected by the other.

Later releases work differently. Once a build is live, an upgrade is not a copy over the top: the old files must be removed first, keeping appsettings.Production.json, web.config and logs\. Leaving old DLLs behind mixes two builds and produces errors such as TypeLoadException or MissingMethodException, often on one screen and hours later. Take a copy of the live folders before overwriting them, so the previous build can be put back.

6.1 Create the application pools

A single application pool named CAS hosts both websites — the API and the SPA. It uses No Managed Code: the API self-hosts .NET through ANCM, and the SPA is static files.

One pool means one worker process for both sites. That keeps configuration simple and gives both sites the same identity and the same NAS and certificate access. The trade-off to remember at deployment time: stopping the pool takes the SPA down as well as the API — requests to the SPA return HTTP 503 while it is stopped. Step 3 is written around that.

6.3 Import the OAuth2 certificates and grant private-key access

The application is its own OAuth2 / OpenID Connect server (OpenIddict) and requires two RSA-2048 certificates — a signing certificate and an encryption certificate — imported into LocalMachine\My on every node, with identical thumbprints. Generation and rotation are covered in docs/deployment/multi-server-deployment.md §2.

Everything in this section can be done in the UI — import, permissions and reading the thumbprint. PowerShell equivalents are given after each part for anyone who prefers them; neither path is required.

6.3.1 Import the two certificates (UI)

Run ▸certlm.msc▸Personal▸Certificates▸right-click▸All Tasks▸Import…
  1. Press Win+R, type certlm.msc and press Enter. This opens Certificates — Local Computer. (Do not use certmgr.msc — that is the current user store, and the app pool cannot read certificates from it.)
  2. Expand Personal, right-click Certificates, then All Tasks ▸ Import…
  3. In the wizard: Store Location is already Local Machine. Browse to CAS-Signing.pfx — change the file-type filter to Personal Information Exchange (*.pfx;*.p12) or the file will not appear.
  4. Enter the PFX password. Leave Mark this key as exportable unticked unless the bank's policy requires it — the application only needs to read the key.
  5. Choose Place all certificates in the following store → Personal. Finish.
  6. Repeat for CAS-Encryption.pfx.
Run on: each app nodePowerShell equivalent
$pw = Read-Host 'PFX password' -AsSecureString
Import-PfxCertificate -FilePath .\CAS-Signing.pfx    -CertStoreLocation Cert:\LocalMachine\My -Password $pw
Import-PfxCertificate -FilePath .\CAS-Encryption.pfx -CertStoreLocation Cert:\LocalMachine\My -Password $pw

6.5 Raise the upload size limit

The application accepts document uploads up to 50 MB (FileStorage:MaxFileSizeBytes = 52,428,800). IIS request filtering, however, rejects anything over its default of 30,000,000 bytes (~28.6 MB) before the request ever reaches the application — the user sees a bare HTTP 404.13 with no message from the app. Raise the limit on the API site.

This setting lives in web.config, which the deploy script preserves. Set it once; it survives releases. If you ever recreate web.config from a fresh publish, re-apply it.

6.6 Confirm the API web.config

The publish output ships a web.config with hostingModel="inprocess", the correct choice here — in-process passes the WebSocket upgrade straight to Kestrel. The server's own copy is preserved by the deploy script and never overwritten.

Run on: each app nodeInspect
Get-Content <APP_ROOT>\api\web.config

# Expect, inside <system.webServer>:
#   <aspNetCore processPath="dotnet" arguments=".\Api.dll"
#               stdoutLogEnabled="false" hostingModel="inprocess" />
#   <requestLimits maxAllowedContentLength="52428800" />   (from §6.5)
Enabling the stdout log for troubleshooting. If the application will not start and the Event Log is not specific enough, temporarily set stdoutLogEnabled="true" and stdoutLogFile=".\logs\stdout", reproduce the failure, then read the file and set it back to false — it grows without limit.

6.7 Verify the SPA site serves deep links

Run on: each app nodePowerShell
# Root document
curl.exe -k -s -o NUL -w "%{http_code}\n" https://localhost:3000/              # 200

# A client-side route that is NOT a real file — proves the rewrite rule works
curl.exe -k -s -o NUL -w "%{http_code}\n" https://localhost:3000/appraisals    # 200, NOT 404
A 404 on the second command means the URL Rewrite module is missing or web.config was not deployed into <APP_ROOT>\web.
